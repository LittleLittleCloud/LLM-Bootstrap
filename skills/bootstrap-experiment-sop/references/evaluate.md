# Evaluate and report

Part of the [experiment SOP](../SKILL.md), whose rules on links, the read-only plugin, and publishing apply here. Resolve links relative to this file.

Read [the experiment protocol](experiment-protocol.md), the frozen experiment (for a derived experiment, its resolved effective experiment), the candidate's runtime and build instructions, and [the evaluation protocol](evaluation-protocol.md), in particular "The endpoint-bench evaluation". If reviewing historical evidence, preserve its original configuration and mark unavailable details rather than rerunning or inventing them.

**Serve the engine.** Start the candidate, and in turn each baseline of the experiment, so that it serves an OpenAI-compatible chat endpoint for the target model, under the conditions the experiment names: hardware, weights, precision, caching, speculation, and limits. Run competing engines serially on the same device, and never two at once on one GPU. The evaluator sees only the endpoint, so verify and write down what it cannot: the deployed runtime and artifact hashes, the actual hardware and settings, the memory and swap you observed, and any deviation from the experiment (a CPU fallback, offloading, a different power mode). These belong in the results pull request description. Costly runs need the user's authorization even when the experiment names them in scope.

**Run the evaluation.** Open the Evaluate page built from the pinned repository revision, in a browser the person or the agent controls. It asks for the endpoint URL, an optional token, and the model, and nothing about the machine or the experiment. Run the `full` profile for a result; `quick` is for development, and its report is preliminary. An agent drives the page through computer use: it enters only what it was given or observed, never invents a value, and never changes evaluator code or edits a report. Export the report, and save it unchanged as `experiments/<experiment-id>/evaluation/<subject>/<name>`, where the subject is `candidate` or the name of the baseline engine. Run each engine more than once when variability matters; every repeated, failed, interrupted, or neutral run is its own report, and none is dropped.

**Check each report.** Read its `status` and `failures`, and the context window source (`assumed` means the long-context tests were sized against a guess). Confirm the required `conform` checks passed: if one failed, no other number of that report can be trusted, and the fix is to the endpoint or the engine, not to the report. Mark each `goal_thresholds` entry passed, failed, or open against the headline metrics; a metric the report lacks is unmet. Apply the experiment's quality gate: `thinking` and `needle` accuracy against the best baseline of the same model, within two standard errors of the difference. Report variability across repeated reports, and keep a single run as preliminary evidence.

Audit comparison conditions before deriving a speedup. Separate matched engine comparisons from best-permitted-system comparisons; disclose precision, speculation, memory limits, cache, context window, profile, and endpoint class differences. Never compare a baseline's `decode` rate with a candidate's `speed` rate. Interactive agent traces can generate different requests, so task time alone does not isolate engine changes.

Report the scores and rates, the gaps to every acceptance criterion, the memory and swap you observed, cost, budget, and human interventions. Verify any self-hosting claim with builder identity, routing and runtime transition, and subsequent development evidence. Historical measurements without trajectories do not prove autonomy.

Create a reviewable results change independently of implementation adoption. The reports follow `EvaluationReport` in [the evaluation schema](../assets/schema/evaluation-protocol.openapi.json) and `experiment.json` follows `Experiment` in [the protocol schema](../assets/schema/experiment-protocol.openapi.json); schema validity shows structure only, not correct measurements or an accepted result. Link source revisions, evidence hashes and access limitations, and failures. State "best among tested configurations" unless baseline coverage supports a bounded SOTA claim. Leave unmet or unmeasured criteria open; results publication does not imply acceptance or authorize merge.

Write the interpretation and feedback for the results pull request description, not for a file in the experiment: failures and their causes, the preflight check that would have caught each, recurring human interventions, suggested skill or evaluation changes, and calibration notes for baselines, budgets, and thresholds. Make suggestions there for a separate review; do not change an evaluation or a skill from inside an experiment.
