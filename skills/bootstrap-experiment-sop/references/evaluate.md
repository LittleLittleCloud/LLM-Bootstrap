# Evaluate and report

Part of the [experiment SOP](../SKILL.md), whose rules on links, the read-only plugin, and publishing apply here. Resolve links relative to this file.

Read [the experiment protocol](experiment-protocol.md), the frozen contract (for a derived contract, its resolved effective contract), and the candidate's runtime/build instructions. Use [the report template](../assets/report-template.md) for results. If reviewing historical evidence, preserve its original configuration and mark unavailable fields rather than rerunning or inventing them.

Verify actual hardware, model hashes, deployed runtime identities, and allowed settings. Run the pinned evaluation as defined in [the evaluation protocol](evaluation-protocol.md): use scripts only from the pinned repository revision, check each against its recorded hash, and keep the result documents they emit unedited. Measure with `engine-evalscope` unless the contract selects a different released evaluation: throughput is the result, and its intelligence scores are compared with a baseline engine of the same model to show the engine did not break the model. Execute baseline/candidate measurements within existing authorization. Run competing GPU loads serially, distinguish warm-up from formal rounds, and retain all failures/repetitions.

Collect the EvalScope summaries of every workload level and the gate outcomes the driver records; report coverage. Compute throughput from sums. Preserve the N−1 versus command-timing distinction and report missing values explicitly. Report intelligence scores with their standard errors, resource gates, and the throughput of every level alongside the headline numbers.

Audit comparison conditions before deriving a speedup. Separate matched engine comparisons from best-permitted-system comparisons; disclose precision, speculation, memory limits, cache, workload, and timing differences. Interactive agent traces can generate different requests, so task time alone does not isolate engine changes. Treat a single cohort as preliminary evidence.

Report benchmark scores, memory/swap, variation, cost, budget, human interventions, and gaps to every acceptance criterion. Verify any self-hosting claim with builder identity, routing/runtime transition, and subsequent development evidence. Historical measurements without trajectories do not prove autonomy.

Create a reviewable results change independently of implementation adoption. When a JSON run record is used, its shape follows the `ExperimentRun` schema in [the protocol schema](../assets/schema/experiment-protocol.openapi.json) and its result documents follow `EvaluationResult` in [the evaluation schema](../assets/schema/evaluation-protocol.openapi.json); schema validity shows structure only, not correct measurements or an accepted result. Link source revisions, evidence hashes/access limitations, and failures. State “best among tested configurations” unless baseline coverage supports a bounded SOTA claim. Leave unmet or unmeasured criteria open; results publication does not imply acceptance or authorize merge.

Fill the report's feedback section from the run: failures and their causes, the preflight check that would have caught each, recurring human interventions, suggested skill or evaluation changes, and calibration notes for baselines, budgets, and thresholds. Make suggestions there for a separate review; do not change an evaluation or a skill from inside an experiment.
