# Evaluate and report

Part of the [experiment SOP](../SKILL.md), whose rules on links, the read-only plugin, and publishing apply here. Resolve links relative to this file.

Read [the experiment protocol](experiment-protocol.md), the frozen experiment (for a derived experiment, its resolved effective experiment), the run instructions of each engine, and [the evaluation protocol](evaluation-protocol.md), in particular "The endpoint-bench evaluation". If reviewing historical evidence, preserve its original configuration and mark unavailable details rather than rerunning or inventing them.

**Serve the engine.** Start the engine of the experiment, at exactly the commit the experiment records, so that it serves an OpenAI-compatible chat endpoint for the target model under the conditions the experiment names. Run engines serially on the same device, and never two at once on one GPU, when several experiments are measured. The evaluator sees only the endpoint, so verify and write down what it cannot: the deployed runtime and artifact hashes, the actual hardware and settings, the memory and swap you observed, and any deviation from the experiment (a CPU fallback, offloading, a different power mode). These belong in the results pull request description. Costly runs need the user's authorization.

**Run the evaluation.** Open the Evaluate page built from the pinned repository revision, in a browser the person or the agent controls. It asks for the endpoint URL, an optional token, and the model, and nothing about the machine or the experiment. Run the `full` profile for a result; `quick` is for development, and its report is preliminary. An agent drives the page through computer use: it enters only what it was given or observed, never invents a value, and never changes evaluator code or edits a report. Export the report, and save it unchanged as `experiments/<experiment-id>/evaluation/<name>`. Run the engine more than once when variability matters; every repeated, failed, interrupted, or neutral run is its own report, and none is dropped.

**Check each report.** Read its `status` and `failures`, and the context window source (`assumed` means the long-context tests were sized against a guess). Reject a report with `build_dirty` and run it again from a clean pinned build. Look at the `conform` checks: if a required one failed, no other number of that report can be trusted, and the fix is to the endpoint or the engine, not to the report. The report is still kept and listed. Work through "Reading a report" in [the evaluation protocol](evaluation-protocol.md): a `thinking` that did not reason, a `speed` run of a few tokens, and a `cache` that never hits are properties of the endpoint to state, not results to claim. Mark each `goal_thresholds` entry met, missed, or open against the headline metrics; a metric the report lacks is open. A regression against the base experiment or an earlier commit is a result: record it and say so. Report variability across repeated reports, and keep a single run as preliminary evidence.

Audit comparison conditions before deriving a speedup. Separate matched comparisons from best-permitted-system comparisons; disclose precision, speculation, memory limits, cache, context window, profile, and endpoint class differences. Never compare one engine's `decode` rate with another's `speed` rate. Interactive agent traces can generate different requests, so task time alone does not isolate engine changes.

Report the scores and rates, the gaps to every goal threshold, and the memory and swap you observed. The reports follow `EvaluationReport` in [the evaluation schema](../assets/schema/evaluation-protocol.openapi.json) and `experiment.json` follows `Experiment` in [the protocol schema](../assets/schema/experiment-protocol.openapi.json); schema validity shows structure only, not correct measurements. Link source revisions, evidence hashes and access limitations, and failures. State "best among tested configurations" unless the experiments compared support a bounded SOTA claim. Leave unmet or unmeasured goals open; results publication does not authorize a merge.

Write the interpretation and feedback for the results pull request description, not for a file in the experiment: failures and their causes, the preflight check that would have caught each, suggested skill or evaluation changes, and calibration notes for goals. Make suggestions there for a separate review; do not change an evaluation or a skill from inside an experiment.
